# Bucket 6.1 — versioned local storage repository

**Status:** complete (module + tests). **Executor:** orchestrator (`/root`). **Date:** 2026-09-15.
**Not yet wired into the workspace** — the save/restore UI lands in 6.3; this bucket is the storage
seam and its failure semantics.

## What shipped

`src/app/project-store.ts`:

- `StoragePort` — the minimal surface needed (`length`, `key`, `getItem`, `setItem`, `removeItem`).
  `window.localStorage` satisfies it, and tests use an in-memory port.
- `createProjectStore(storage, { prefix, storeVersion })` — namespaced keys under
  `planlab:v1:` (`planlab:v1:project`, `planlab:v1:recovery:*`). The supported store version is
  injectable so the migration seam of bucket 6.2 can be exercised before a v2 exists.
- `read()` returns a typed outcome and never throws:
  - `loaded` — a v1 document whose `project` also survives `tryNormalizeProject()`, i.e. the same
    runtime validation a worker message gets;
  - `empty` — nothing stored yet;
  - `corrupt` — unparseable JSON, a missing/!integer version, or a document that fails validation,
    with a reason string;
  - `unsupportedVersion` — written by a newer build; never guessed at, never overwritten;
  - `outdated` — an older store version, left untouched for 6.2 to migrate;
  - `unavailable` — the store itself refused to answer (denied, disabled, security error).
- `write(project, savedAt?)` returns `saved` with the ISO timestamp or `failed` with the reason, so a
  quota-exceeded or denied store becomes copy rather than an exception.
- `clear()` removes only keys under this prefix and returns exactly what it removed; `ownedKeys()`
  enumerates them, and a store that cannot enumerate reports none rather than assuming it may delete
  what it cannot see.
- `preserveUnreadableDocument()` moves an unreadable document to a timestamped recovery key instead of
  deleting it (the storage half of bucket 6.2; the migration half is still to do).

## Design notes

- A stored value is treated as untrusted input, for the same reason a worker message is: it may have
  been written by another build, edited by hand, or truncated by a full disk.
- `storeVersion` (the storage document) is deliberately separate from `schemaVersion` (the brief
  schema in `src/domain/model.ts`). The first describes the envelope the app wrote; the second is
  domain data validated by normalization.
- Recovery keys are timestamped, so a second failure can never overwrite the first copy.

## Evidence

- `npm test` — **185 passing** (176 before this bucket; +9 store tests).
- `npm run typecheck` clean, `npm run build` clean.
- Tests cover: round-trip equality with the canonical brief; empty store; invalid JSON; a JSON object
  that is not a brief; a missing version; a future version (and that a read does not overwrite it); an
  outdated version seen by a newer reader; denied reads; full/denied writes; reset touching a planted
  foreign key; namespaced `ownedKeys()`; preservation under unique recovery keys; and prefix isolation
  between two stores sharing one storage object.

## Not done here (deliberately)

- Migrations between store versions (6.2).
- Autosave, flush and save-status projection (6.3).
- The reset flow and its confirmation copy — that copy is a user hard gate (6.4).
