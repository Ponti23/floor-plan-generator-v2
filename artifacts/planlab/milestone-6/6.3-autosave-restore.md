# Bucket 6.3 — debounced autosave, flush, and restore on load

**Status:** complete. **Executor:** orchestrator (`/root`). **Date:** 2026-09-15.
This bucket wires the 6.1 store into the workspace, so local persistence is now a live behaviour
rather than a tested module.

## What shipped

`src/app/main.ts`:

- **Restore on load.** The store is read once at boot. A `loaded` document becomes the editor's
  starting brief; every other outcome keeps the canonical default and, where there is something to
  say, shows a notice in the brief pane (`role="status"`).
- **Corrupt documents are preserved, not overwritten.** A corrupt read calls
  `preserveUnreadableDocument()`, which moves the raw text to a timestamped recovery key before the
  live key can be rewritten by the next save.
- **Debounced autosave.** `commitEditorDraft()` schedules a write when the committed revision
  actually changed (400 ms debounce). The written value is `editor.committedBrief` — the authored
  document — not the normalized solver input, so a reopened project is the form the author typed.
- **Immediate flush.** Generate flushes before starting a run, and `pagehide` / `beforeunload` flush
  as well: a debounce that never fires is a lost project.
- **Save status** in the toolbar: `Saved locally` / `Saving…` / `Local save failed` /
  `Local saving unavailable`, with the dot turning amber on failure and grey when storage is
  unreachable. The label is written in place by `renderSaveStatus()`, so a save never re-renders the
  form under the cursor.
- **`unavailable` is a first-class state:** a browser that refuses storage still gets a working
  workspace, and the notice says plainly that edits will not survive a refresh.

`src/app/project-store.ts` gained `storageNoticeKind(outcome)`, the pure mapping from read outcome to
the notice the UI shows. `src/app/presentation-copy.ts` gained a `storage` group (labels + notices),
replaceable like the rest of the copy.

## Limits, stated honestly

- The debounce/flush logic itself lives in `main.ts` and is verified only in the browser, not by a
  unit test: the projection it depends on (`storageNoticeKind`, the store outcomes) is unit-tested,
  but "the timer fired at the right moment" is a browser observation.
- Denied storage is unit-tested at the store level and rendered by the same code path, but it has not
  been simulated in a browser (the harness cannot easily revoke `localStorage` mid-run).
- **Bucket 6.2 is not done.** There is no migration yet: an older stored document is reported as
  `outdated`, kept, and not loaded. That is safe but not yet useful, and 6.2 owns it.
- Reset is still absent (6.4), and its confirmation wording is a user hard gate; the toolbar's "New"
  control stays disabled until then.
