# Bucket 6.5 — stored results and engine-version invalidation

**Status:** complete. **Executor:** orchestrator (`/root`). **Date:** 2026-09-15.

## The problem this bucket had to solve first

The canonical payload for a full run is **3,403,986 bytes** — 300 candidates, each carrying three
scorecards. Writing that on every generation would sit uncomfortably close to a browser's per-origin
storage limit, and the workspace only ever displays the three selected layouts. So the stored document
is a projection, in the same spirit as the Stage 3 D4 payload projection.

## What shipped

`src/app/stored-result.ts`:

- `projectStoredResult(payload)` keeps: `payloadVersion`, `ok`, the **selected layouts only**, their
  candidate scorecards, the selection summary, the run metadata, and a version block. Diagnostics
  detail and the unfilled candidate pool are dropped rather than stored and ignored.
- Measured on the canonical full budget: **3,403,986 → 35,967 bytes** (3 of 300 candidates kept).
  The stored brief is another ~2.6 KB.
- `CURRENT_RESULT_VERSIONS` / `versionsMatch()` compare the seven versions that can change what a
  score means: payload, engine, rule, scoring, calibration, determinism, and budget. A stored result is
  restored only when **every** one matches; each key has its own falsification test.
- `readStoredResult(raw)` classifies a stored document as `empty`, `usable`, `outdated` (written by a
  different build) or `corrupt`, without throwing.

`src/worker/controller.ts`: `restore(payload)` adopts an already-validated payload and maps it to the
same statuses the worker path uses (`complete` / `partial` / `infeasible`).

`src/app/main.ts`:

- On boot, a stored result is adopted **only when the brief was also loaded** — a result restored
  against a different brief would present old layouts as the answer to the current one.
- A result is persisted once it belongs to the current committed revision, under
  `planlab:v1:result` (same namespace, so a reset removes it too).
- **Generate now forces a brief save** even when the revision has not moved: a stored result is
  useless without the brief it belongs to, and this was a real defect found by the reload test — the
  first attempt stored the result and no brief, and restore correctly refused.
- An outdated or corrupt stored result is deleted and the workspace says so, using
  `storage.notices.resultsOutdated`.

## Evidence

- `npm test` — **197 passing** (+8 over 6.4: five stored-result tests and three migration tests).
  `npm run typecheck` clean, `npm run build` clean, `npm run diagnostics:canonical -- --check` clean at
  `sha256:8efe5b5e…` (the domain is untouched).
- **Browser, real reload** (`scripts/capture-ui.mjs --post … --reload`, one Chrome profile):
  generate → storage holds `planlab:v1:project` (2,579 bytes) and `planlab:v1:result` (35,967 bytes) →
  reload → `statusDetail: "Complete · Three compatible layout options ready."`, three option cards
  restored (Compact Efficiency 81 selected), summary `81/100`, metric rows and score bars present, no
  notice. Capture `6.5-restored-result.png`.
- **Browser, version invalidation:** tampered the stored `engineVersion` to `planlab-generator-0.3`,
  reloaded → no option cards, no summary, brief intact, and the notice "The layouts from the previous
  session were generated by a different build, so they were discarded and need regenerating."
  Capture `6.5-outdated-result.png`.

## Limits, stated honestly

- The panel's restored state is verified by DOM digest after a real reload, but the restored payload
  is not re-scored: it is trusted exactly when the seven versions match, which is the point of the
  bucket.
- A store that is full will fail the result write silently (the brief save reports it). Writing 36 KB
  per generation is not free, and a future bucket could keep only the selected option that is on
  screen if profiling says so.
