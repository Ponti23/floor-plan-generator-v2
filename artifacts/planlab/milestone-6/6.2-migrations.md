# Bucket 6.2 — sequential migrations

**Status:** mechanism complete and tested; **no migration is registered yet, because only store
version 1 has ever existed.** **Executor:** orchestrator (`/root`). **Date:** 2026-09-15.

## What shipped

`src/app/project-store.ts`:

- `StoreMigration { from, to, migrate(document) }` and `store.migrate(): MigrationOutcome`
  (`notNeeded` | `migrated` | `failed`).
- `createProjectStore(storage, { migrations, storeVersion })` applies registered steps **one version
  at a time** until the document reaches the supported version.
- A document is rewritten **only after every step has succeeded**. A missing step, a throwing step, a
  step that returns nothing, a document from a newer build, and unparseable JSON each return
  `failed` with the original bytes untouched in storage.
- The recovery-key half of this bucket already landed in 6.1: `preserveUnreadableDocument()` moves an
  unreadable document to a timestamped `planlab:v1:recovery:*` key instead of deleting it.

## Why no migration is registered

Nothing in this build has ever written a store version other than 1, so a v0→v1 migration would be
invented data — exactly the kind of thing the mockup brief forbids for geometry, and the same
principle applies to storage. The seam is real and tested with injected migrations; the first genuine
migration belongs with the first genuine format change.

## Evidence

- `npm test` — 197 passing, of which 3 tests exercise migrations directly: a two-step v1→v2→v3 chain
  (asserting the migrated document, the rewritten version, and `notNeeded` on a second run), a missing
  step, a throwing step, a step returning nothing, and a document from a newer build — each asserting
  the stored bytes are unchanged after the failure.
- `npm run typecheck` clean, `npm run build` clean.
